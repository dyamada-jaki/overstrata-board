# Issue を実装する

- 以下の `N` は、人間が渡した Issue 番号（Claude Code では $ARGUMENTS）。渡されていなければ聞く
- このスキルの本体は `.claude/skills/implement-issue/`。Codex 用の `.agents/skills/implement-issue` はこのフォルダへのシンボリックリンクなので、直すのはここだけでよい
- プロジェクト固有の値（リポジトリ・確認コマンド・ポート・画面確認の幅など）は、CLAUDE.md（Codex では AGENTS.md）の「開発設定」から読む。このスキルには直接書かない
- 以下の `orca` は、そのセッションで動作確認し、Orca のスキルを読むために使った実行ファイルに置き換える。PATH 上の同名コマンドが使えるとは仮定しない

次の5手順を順番に行う。手順3で承認をもらうまで、コードを書かない。

## 1. Issue を読む
- `gh issue view N --json title,body,comments` で本文とコメントを読む
- 目的・受け入れ条件・スコープ外・前提（着手条件）を確認する
- `docs/next-issues.md` と前回・依存Issueのレポートを読み、今回試す改善・持ち越した確認・担当と確認時点を拾う。実機確認の持ち越しだけを、新しい着手条件と推測しない
- 着手条件に、未完了の Issue や「確認中」「未決」の仕様が残っていたら、実装せずに止めて人間に伝える

## 2. 仕様を読む
- `docs/spec.md` のうち、Issue がリンクしている箇所を読む。画面を含む Issue では「2.4 画面の前提」も読む
- `CLAUDE.md`（Codex では `AGENTS.md`）の「守ること」と「開発設定」を確認する
- `docs/testing.md` を読み、テストの分担・TDD・モック・検証の証拠の方針を確認する

## 3. 実装計画を出して、承認を待つ
次を書いた計画を出し、人間の承認を待つ。
- 受け入れ条件ごとに、どう満たすか
- 作る・変えるファイル
- 書くテスト（**機能追加・振る舞いの変更では実装より先に書く**）。`docs/testing.md` 2章の層から選ぶ（主役は画面操作の結合テスト。domain の単体テストは条件に当たる関数だけ）。受け入れ条件ごとに、検証する層と、仕様から決めた代表的な入力・操作・期待結果を示す。振る舞いを変えない整理など、テスト先行の対象外・例外は同1章に従って検証方法を示す
  - 計算の境界や期待一覧、画面の状態遷移は `docs/testing.md` に従って選ぶ。特に間違えやすい壊れ方の具体例と、仕様上の期待・検出方法を対応させる。実装を読んで出力を正解として写さない
  - 実物の部品・状態・domain 関数を組み合わせる。モック等が必要なら、境界・理由・実物との接続を確かめる方法を書く
  - E2E の導入状況と、追加・更新する重要な操作フローを確認する。未導入／対象外ならその理由を書く。環境導入を別の機能 Issue に混ぜない
  - ミューテーションテストは `docs/testing.md` 7章に従い、導入状況・対象範囲・見つけたい誤りを確認する。未導入の基盤を今回の機能Issueへ混ぜない
- 画面を含む場合: 画面の確認方法（使う環境、確かめる画面幅と操作）
- 前回の改善のうち今回試すものと、効果を確認する場面・観測する結果。該当するものがなければ、その旨を書く
- 確認したいこと（spec.md や Issue から読み取れない点）

spec.md に書かれていないルールを決めないと進めない場合は、推測で埋めずに質問して止まる。

## 4. 実装して確かめる
- 承認された計画どおりに実装する。スコープ外のことはしない
- **機能追加・振る舞いの変更ではテストを先に書く**: 計画のテストを書いて実行し、対象の振る舞いが未実装、または誤っているために失敗することを確かめる。未実装の画面要素が見つからないことも含む。環境設定の不備や無関係な import・型エラーは証拠にしない（空の枠だけ先に作ってよい）。失敗の出力の要点を控え、`test: ...` として実装より前にコミットする
- 次にその振る舞いを実装してテストを通し、別のコミットにする。先に書いたテストを実装に合わせて弱めない。期待値を変えるなら仕様上の根拠を残す
- 振る舞いを変えないリファクタリングでは、既存テストが変更前後で通ることを確かめる。不足するテストは変更前に追加して通し、新しい失敗は求めない。その他の対象外・例外も `docs/testing.md` 1章に従う
- 不具合修正は、再現テストの失敗を先に確かめる（自動化できない場合の扱いも `docs/testing.md` に従う）
- CLAUDE.md（AGENTS.md）の「開発設定」の確認コマンドがすべて通るまで直す
- ミューテーションテストが導入済みで対象となる場合は、通常テストの成功後にREADMEの手順で実行する。生き残った変異を `docs/testing.md` 7章に従って分類し、意味のある検証不足を補強して再確認する。テストの粒度と仕様から決めた期待を維持する
- E2E が導入済みで変更の対象となる場合は、README にあるコマンドで実行する。未導入なら存在しないコマンドを要求しない。画面を含む変更では、RTL と実際の画面確認の結果、E2E 化の残作業を記録する
- 画面を含む場合は、テストとは別に、**実際の画面**で表示と操作を確かめる（spec.md 2.4。DOM のテストだけで「画面確認済み」としない）
  1. 「開発設定」の開発サーバーを起動する（ポートは `.env` の `HOST_PORT`）
  2. Orca のブラウザで開く: `orca tab create --url http://localhost:<ポート> --json`。操作の仕方は `orca skills get orca-cli --reference references/browser.md` を読む
  3. 「開発設定」のスマホ幅にする。使用中の Orca のヘルプで端末プリセットを確認し、利用できなければ `orca exec --command "set viewport <幅> <高さ>" --json` で幅を指定する。`orca eval --expression "({ width: window.innerWidth, height: window.innerHeight })" --json` で実際の寸法を確かめる。確認対象のタブを維持し、マウス操作・タッチのエミュレーション・実機を区別して記録する。指定幅にできなければ、実際の幅と未確認項目を残す
  4. Issue の受け入れ条件にある操作（タップ・選択・移動など）を `orca snapshot` と `orca click` で行い、操作直後の表示・選択状態を確認する。成功応答でも画面へ入力が届かない場合があるため、反応が不明なら対象タブとイベントの到達を確かめ、現在のヘルプにある別の入力方法（マウス操作など）を試す。`orca screenshot` で見た目と横スクロールの有無も確かめる
  5. PC 幅でも崩れないことを確かめる
  6. 確認が終わったら `docker compose down` で止める
  - Orca のブラウザが使えないなど、確かめられなかったときは、その理由と未確認の項目を記録して先に進む（手順5で PR に書く）
- スマホ実機での確認はしなくてよい。レビューのときに人間が行う

## 5. 証拠を付けて PR を作る
`gh pr create` で PR を作る。本文には次を書く。
- 何をしたか
  - 承認した計画の要点と、確認事項の決着。計画から変えた点があれば、その理由
  - 今回試した前回の改善と観測結果、試せなかったものと理由。持ち越す確認は担当・確認時点・元の記録への参照を残す
- どう確認したか
  - テスト先行の対象では、テストのコミットと実装のコミット、実装前にテストが失敗した結果の要点。先に書けなかったテストや対象外・例外があれば、その理由と実施した確認（振る舞いを変えない整理では変更前後の成功）
  - 確認対象のコミット、テストの実行コマンド・環境・結果。受け入れ条件をどのテストで確かめたか。E2E の結果、または未実施／対象外の理由
  - モック等を使った理由と実物との接続確認、期待値を変更した場合の根拠（該当するときだけ）
  - ミューテーションテストの対象・結果・レポート・残件と判断の根拠（`docs/testing.md` 7章）。未導入／対象外なら理由を記載する
  - 画面を含む場合: 使った環境（Orca のブラウザ・端末の指定など）、画面幅、行った操作、結果。スクリーンショットを撮ったなら、その説明
  - レイアウトの寸法を確認の根拠にする場合は、その画面幅での実測値と測定方法を記載する。計算値・CSS の宣言値は実測値と区別し、実際の表示を確認した証拠として代用しない
  - スマホ実機での確認は未実施で、レビュー時に人間が行うこと
- 確認したいこと（なければ「なし」）
  - 受け入れ条件のうち、自分で確かめられなかったもの（実機・ブラウザの目視など）は必ずここに書く。「なし」と書けるのは、すべて確かめたときだけ
- `Closes #N`
