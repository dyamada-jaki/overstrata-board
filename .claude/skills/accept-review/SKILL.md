# PR の受け入れを一次判断する（PO）

あなたは **PO**。コードの良し悪しではなく、**欲しかったものになっているか**を見る。コードのレビューは開発チームの相互レビュー・品質レビューが済ませている。

- 以下の `P` は PR 番号、`R` は開発チームの Run ID（Claude Code では $ARGUMENTS の1つ目と2つ目）。`R` が無ければ、開発チームへの返事は省き、人間にだけ伝える
- このスキルの本体は `.claude/skills/accept-review/`。Codex 用の `.agents/skills/accept-review` はこのフォルダへのシンボリックリンクなので、直すのはここだけでよい
- プロジェクト固有の値は、CLAUDE.md（Codex では AGENTS.md）の「開発設定」から読む
- 人間が呼んだとき、または開発チームが送ってきたときだけ使う（Claude Code は `disable-model-invocation`、Codex は `agents/openai.yaml` で自動の呼び出しを止めている）
- **ファイルを変えない。** spec.md の更新や Issue の登録が必要だと分かっても、ここでは判断の材料として書くだけにし、人間と相談してから行う
- 人間と話している途中にこの指示が届いたら、区切りのよいところで受け入れ確認を先に済ませ、終わったら元の話に戻る

## 1. 読む
- `gh pr view P --json number,title,body,headRefOid,url,comments` で PR 本文とコメントを読む。対象の head SHA を控える
  - 開発チームの「開発チームの推薦」コメント（比較・一次判断・残っている指摘）
  - 相互レビュー・品質レビューのコメントは、結論と必須指摘の扱いだけ確かめる。読み直してコードレビューをやり直さない
- PR 本文の `Closes #番号` から Issue 番号 `N` を取り、`gh issue view N --json title,body,comments` で目的・受け入れ条件・スコープ外を読む
- Issue 番号が分かったら、`bash .claude/skills/dual-implement/scripts/dev-team.sh mark N PO 受け入れ確認` を実行する（開発チームが作業時間を集計するため）
- `docs/spec.md` のうち、Issue がリンクしている箇所を読む
- `docs/issue-reports/issue-N.md` があれば、承認した計画と確認事項の決着を読む
- 前の受け入れ確認（このスキルのコメント）があれば読み、何回目の確認かを数える

## 2. 判断する
次の観点だけを見る。それぞれ「よい / 問題あり / 確かめられない」と根拠を付ける。

1. **受け入れ条件**: 条件ごとに、満たした証拠（テスト・CI・エージェントの画面確認の記録）が PR かレビューにあるか。証拠が無い・古い SHA のものだけ、は問題とする。ただし、前の SHA からの差分が `.md` のファイルだけで、開発チームの推薦にそう書かれていれば、前の SHA の CI の成功と実行中の CI を証拠としてよい（CI の成功は finish-issue のマージ前に確かめる）
2. **仕様どおりか**: spec.md と食い違っていないか。spec.md や Issue に無いルールを、推測で決めて実装していないか
3. **スコープ**: Issue の「スコープ外」に手を出していないか。足りない分を黙って次へ回していないか
4. **使う人から見た振る舞い**: 画面を含む場合、PR の画面確認の記録（操作と結果）が、spec.md の画面の前提と Issue の目的に合っているか。スマホ実機の確認は人間が行うので、ここでは「人間に確かめてほしい点」を挙げる
5. **確認したいこと**: PR と開発チームの推薦にある「確認したいこと」に、仕様を決める必要があるものが無いか。あれば、決めずに人間へ回す

判定は次のどれか。
- **受け入れ**: 問題なし。人間が採用を判断してよい
- **差し戻し**: 開発チームが直せば受け入れられる。直してほしい点を、観点・根拠・期待する状態で具体的に書く（好みや、Issue に無い追加の要望で差し戻さない）
- **人間の判断が必要**: 仕様を決めないと判断できない、または差し戻しが3回目になる

## 3. PR にコメントする
`gh pr comment P --body-file <一時ファイル>` で投稿する（ファイルはリポジトリの外に書く）。
```
受け入れ一次判断（PO）: <受け入れ / 差し戻し / 人間の判断が必要>（<回数>回目）
対象: Issue #N / head <SHA>

| 観点 | 結果 | 根拠 |
|---|---|---|
| 受け入れ条件 | … | … |
| 仕様どおりか | … | … |
| スコープ | … | … |
| 使う人から見た振る舞い | … | … |
| 確認したいこと | … | … |

差し戻しの内容（差し戻しのときだけ）: 1件ずつ、直してほしい点・根拠・期待する状態
人間に確かめてほしいこと: 実機で見てほしい点、仕様を決める必要がある点
spec.md・Issue に戻す候補（あれば）: 人間と相談してから PO が反映する
```

## 4. 開発チームに返す
`R` があれば、開発チームの Run に返す。
```
orca orchestration send --to run:R --type handoff \
  --subject "#N 受け入れ一次判断: <受け入れ / 差し戻し / 人間の判断が必要>" \
  --body "<コメントの URL>。<差し戻しなら、直してほしい点の要約>"
```
送れなかったら、その旨と判定を人間に伝える。送ったあと（`R` が無ければコメントのあと）、`dev-team.sh mark N PO 終了` を実行する。

## 5. 人間に伝える
この端末で、判定とコメントへのリンクを3行ほどで伝える。spec.md・Issue に戻す候補があれば、相談したいこととして添える。
