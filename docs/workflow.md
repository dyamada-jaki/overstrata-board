# 戦闘ボード開発の進め方（Spec × Issue × Orca）

仕様の全体像は `docs/spec.md` に持つ。そこから**今すぐ作る一片だけ**をIssueに切り出し、Orcaで1本ずつ実装する。

- `docs/spec.md` … アプリ全体の「何を・なぜ・どこまで」を持つ地図。まだ作らない部分も書いてよい
- Issue … 地図から今作る一片だけを切り出した作業票。1〜3本ずつ出し、終わったら次を切る
- [docs/testing.md](testing.md) … テストの層・TDD・モックとレビューの分担を決める共通方針
- [docs/issue-reports/](issue-reports/README.md) … 1 Issue につき1ファイルで、計画・承認・検証・採用理由・後片付け・改善の反映先を残す記録

---

## 3つの席

| 席 | 場所 | 寿命 | やること | 書いてよいもの |
|---|---|---|---|---|
| **PO**（プロダクトオーナー） | Orca の main の worktree の端末（Claude Code か Codex。vault も参照先に追加） | 長く使う。状態はファイルに置き、いつ開き直してもよい | 人間と議論する、spec.md を書く、Issue を切って順番を決め「開発可」を付ける、開発チームの推薦を受け入れ一次判断する（`accept-review`） | spec.md、Issue とラベル、next-issues.md（PO だけが書く）、PR への受け入れコメント |
| **開発チーム**（コーディネーター） | Orca の main の worktree の端末。起動係か人間が Issue ごとに開く | Issue 1本（着手からふりかえりまで）。終わったら閉じる | `dual-implement` で開発者に実装・レビューさせて一次判断し、PO の確認を経て人間に報告する。`finish-issue` でマージ・後片付け・ふりかえり | Issue レポート（「PO への申し送り」を含む）、Issue への申し送りのコメント、スキル・CLAUDE.md など（承認された改善だけ。他の開発チームが動いておらず、PO の書きかけが無いとき） |
| **開発者** | dual-implement が作る worktree（Claude Code と Codex） | 実装からマージまで | 実装・PR・レビュー | 自分の worktree のコード |

ファイルの置き場所は GitHub のリポジトリ1つ。PO と開発チームは同じ main の worktree で動くので、同じファイルを同時に書かないよう、書くファイルを席ごとに分ける。
- next-issues.md・spec.md は PO だけが書く。開発チームは Issue レポートとコメントで申し送る
- 開発チームがそれ以外の共有のファイルを直すときは、先に `git status --porcelain -- <ファイル>` で PO の書きかけが無いことを確かめる。PO は書きかけを長く残さず、区切りごとにコミットする
- コミットは直したファイルをパスで指定し、push の前に `git pull --rebase --autostash` する

人間の関所は3つ: ④計画承認（開発チームが聞く）、⑥採用の判断（PO の受け入れ確認のあと）、⑧改善の採否。

### 受け渡し
- 判断の本文は GitHub に残す（開発チームの推薦と PO の受け入れ判断は PR コメント）。端末どうしのやりとりは合図だけにする
- 開発チーム → PO: `orca terminal send` で PO の端末に `/accept-review <PR番号> <Run ID>` を送る。PO の端末は `dev-team.sh po-find` で探す
- PO → 開発チーム: `orca orchestration send --to run:<Run ID> --type handoff` で判定を返す
- 差し戻しは2回まで。3回目は人間に判断を仰ぐ
- ふりかえりで出た spec.md と Issue の案、next-issues.md の「現在地」に載せる内容: 開発チームが Issue レポートの「PO への申し送り」に書き、Issue にコメントして PO に一言送る。PO が next-issues.md・spec.md・Issue に反映する
- 2026-10-18 に Claude Code の端末どうしで動作を確認した。Codex の PO 端末で `gh`・`.git` への書き込み・`orca` が使えることも確かめた。開発チームから Codex の PO へ `$accept-review` を送る受け渡しと、開発チームを Codex にした場合は未確認

### PO を開く
- 新しい worktree は作らない。Orca で main の worktree（リポジトリの元のフォルダ）を選び、ターミナルを開く
- Claude Code なら `claude --model opus --effort high` で起動する。Codex なら Orca からエージェントとして起動する（素の `codex` は `.git` への書き込みとネットワークが制限され、PO の登録や `gh` が失敗する）
- 最初に次を実行させ、3つとも通ることを確かめる。2つ目は、この端末を PO として登録する（開発チームはこれで PO を見つける）。開き直したら、そのたびに登録し直す
  ```
  gh api user -q .login
  bash .claude/skills/dual-implement/scripts/dev-team.sh po-register
  /Applications/Orca.app/Contents/Resources/bin/orca terminal show --terminal "$ORCA_TERMINAL_HANDLE" --json
  ```
- PO の席は会話の記憶を引き継がない。経緯は spec.md・next-issues.md・Issue に書いておき、開き直したら最初に読ませる

### 開発チームを開く（起動係）
- PO か人間が、着手条件のそろった Issue に「開発可」を付ける
- Orca の定期実行「開発チーム起動」が15分おきに `dev-team.sh precheck` で確かめる。「開発可」の Issue があり、「着手中」の Issue も動いている開発チームも無いときだけ、起動係のエージェントが `dev-team.sh launch` を実行する。条件に合わないときはエージェントを起動しないので、費用はかからない
- launch は、番号のいちばん小さい「開発可」の Issue を「着手中」に替え、main の worktree に開発チームの端末（`claude --model opus --effort high`）を開いて `/dual-implement N` を送る。定期実行のセッションは応答のあと Orca が自動で閉じるが、開発チームは別の端末なので残る
- 手で始めるときは、main の worktree の端末で `/dual-implement N` を打つ。dual-implement の最初に `dev-team.sh claim N` で登録される
- 開発チームは同時に1つまで（なるべく並行しない）。finish-issue の最後の `dev-team.sh release N` で登録が外れ、次の「開発可」が拾われる

定期実行は Orca の設定で Git に残らないので、作り方をここに控える。
```
orca automations create --name "開発チーム起動" --trigger "*/15 * * * *" --disabled \
  --workspace path:<main の worktree の絶対パス> --workspace-mode existing --fresh-session \
  --provider claude --extra-agent-args="--model haiku" \
  --precheck "bash .claude/skills/dual-implement/scripts/dev-team.sh precheck" \
  --prompt "起動係です。ファイルは変更しないでください。bash .claude/skills/dual-implement/scripts/dev-team.sh launch を1回だけ実行し、出力をそのまま報告して終わってください。"
```
有効にする: `orca automations edit --id <ID> --enabled`（止めるときは `--disabled`）。時間帯を絞るなら `--trigger "*/15 9-22 * * *"` のようにする。手動の `orca automations run` は precheck を行わないので、試すときは定期の実行で確かめる。

## 毎回まわすサイクル（8ステップ）

```
① 議論 → ② 切り出し → ③ 着手 → ④ 計画承認 → ⑤ 実装 → ⑥ レビュー → ⑦ マージ → ⑧ ふりかえり ─┐
  ↑                                                                                   │
  └───────────────────────────────────────────────────────────────────────────────────┘
    （PO）           （PO）          （開発チーム ③〜⑦。⑥で PO が受け入れ確認）            （開発チーム・PO）
```

`finish-issue` を使う場合は、開発チームが⑦から⑧のふりかえりまで行い、結果と具体的な改善案を会話で示す。人間が採否を判断した後、承認された改善を反映する。spec.md と Issue の案は PO へ申し送り、PO が人間と議論して反映する。

### Issueと区切りの確認

Issueごとのサイクルに加えて、spec.md 4章の区切りでは、複数Issueをつないだ完成形を利用者が確認する。進行状況とレポートでは次の状態を分ける。

| 状態 | 判定に使う証拠 |
|---|---|
| 実装・自動検証 | 受け入れ条件、テスト・CI・エージェントによる画面確認の結果 |
| mainへの取り込み | マージしたPRとコミット。Issueが閉じたことはこの処理の記録 |
| 人間による実機確認 | 確認待ち／確認済み／問題あり／対象外。対象コミット、端末・環境、操作、結果をPRまたはIssueレポートに残す |
| 区切りの達成 | spec.mdの「達成の確認」にある一連の操作が期待どおり動き、その区切りに必要な持ち越し確認も合格した証拠。未達／確認待ち／達成を記録する |

人間の判断で実機未確認のままマージしても、実機確認済み・区切り達成とはしない。開発チームは未確認項目・担当・次に確認する時点・記録先を PO へ申し送り、PO が `docs/next-issues.md` に引き継ぐ。詳細の正本は元のIssue／レポートとし、次のIssueへリンクする。対象の挙動に影響する変更が入った場合は再確認する。

区切り1では、#8の盤面・ラベル・指での操作の確認を持ち越している。#9のキャラ表示・移動まで実装した時点で、利用者がスマホで範囲内外への移動・選択切り替え・解除まで通して確認し、開発チームが#9のレポートに達成／未達・残件を記録して PO へ申し送り、PO が現在地に反映する。確認結果から次の仕様や優先順位を見直し、実施前のチェック項目を完了扱いにしない。

### ステップ1：議論する【PO】
- **入力**：前回のふりかえりで出た気づき、または新しくやりたいこと
- 前回・依存Issueのレポートと `docs/next-issues.md` から、今回試す改善と持ち越した確認を拾う。今回に関係する改善について、どの場面で何を観測すれば役立ったと判断できるかを計画へ引き継ぐ
- **やること**：AIが相棒に質問して、決めるべき点を洗い出す
  - 例：「すり抜けはできる？」「前衛は動く壁って、敵の移動を止めるの？」
- **出力**：`docs/spec.md` の更新。決まったことを書き足し、未決事項から消す
- **なぜ**：全体像を1か所に保つため。会話は消えるけど、spec.mdは残る

チェック：
- [ ] 決まったことを spec.md に書いた
- [ ] 未決事項の一覧を更新した
- [ ] mainにコミットした

### ステップ2：Issueを切り出す【PO】
- **やること**：spec.mdの中から「今すぐ作る一片」を1〜3本選ぶ
- **選ぶ基準**（3つとも満たすもの）
  1. 前提がそろっている（依存しているものが完成済み）
  2. PR1本で終わる大きさ
  3. 完成したかどうかを確かめられる（テスト、または画面で見て分かる）
- **区切り1の先行登録（2026-10-14）**：利用者の希望により、区切り1の残りはまとめて登録する。依存先が未完了でも登録できるが、Issue の「前提・着手条件」に依存先と未決事項を明記する。基準1は実装に着手する時点で満たすこと。未決の仕様は着手前に spec.md へ反映する。PR1本の大きさと確認可能な受け入れ条件は、先行登録でも維持する
- **Issueに書くこと**
  - 目的（1〜2行）
  - spec.mdの該当箇所へのリンク
  - 受け入れ条件（チェックボックス）
  - スコープ外（やらないこと）
  - 画面がある場合、エージェントの確認と人間の実機レビューを分けて記載する。実機での操作をエージェントの PR 作成条件にしない
- **Issueに書かないこと**
  - 関数名やファイル構成などの実装方法 → エージェントがステップ4で自分で考える
- **出力**：AIが `gh issue create` でGitHubに登録する
- **着手の合図**：着手条件がそろった Issue に「開発可」のラベルを付ける。付けると起動係が開発チームを開く。順番を決めるのは PO で、起動係は番号の小さいものから拾う
- **なぜ短く保つか**：詳しい内容はspec.mdにある。Issueに写すと二重管理になって、片方だけが古くなる

チェック：
- [ ] 選んだIssueが3つの基準を満たしている
- [ ] Issueにspec.mdへのリンクがある
- [ ] 受け入れ条件とスコープ外が書いてある
- [ ] GitHubに登録された
- [ ] 着手してよい Issue に「開発可」を付けた（着手条件がそろっているものだけ）

### ステップ3：着手する【開発チーム】
- 「開発可」の Issue を起動係が見つけ、開発チームの端末を開いて `/dual-implement 番号` を送る（→「3つの席」の「開発チームを開く」）
- 手で始めるときは、Orca の main の worktree の端末で `/dual-implement 番号` を打つ。1本だけ試すなら、新しい worktree で `/implement-issue 番号` でもよい

**なぜ1行で済むか**：手順はスキルに、仕様はspec.mdに、作業範囲はIssueに書いてあるから。毎回長い指示を書かなくていい。

### ステップ4：計画を承認する【開発チーム】★ここが関所
エージェントは、すぐにはコードを書かない。まず「こう作ります」という計画を出してくる。

相棒はIssueと見比べて確認する：
- [ ] 受け入れ条件を全部カバーしているか
- [ ] 仕様から期待結果を決め、各条件をどの層のテスト・画面確認で確かめるかが明確か（[テスト方針](testing.md)）
- [ ] 特に間違えやすい振る舞いについて、壊れ方の具体例と、それを検出するテスト・確認方法が対応しているか。前回の改善を試す場面も明確か
- [ ] スコープ外のことをやろうとしていないか
- [ ] エージェントが「確認したいこと」を挙げていないか

**分岐**：
- 計画が妥当 → 承認してステップ5へ
- 小さな疑問 → その場で答える
- 仕様の穴が見つかった → **実装を止めて PO に戻す**。PO と spec.md・Issue を直してから、もう一度「開発可」を付ける

**なぜここが関所か**：Issueの曖昧さは計画に表れる。コードになる前に見つけるのがいちばん安い。

承認した計画の要点と、確認事項の決着を控える。通常の実装では PR 本文に、dual-implement ではコーディネーターのレポートに残し、後から承認内容を追えるようにする。

### ステップ5：実装【開発者・エージェントが自走】
- [テスト方針](testing.md)に従って実装し、テスト・型チェック・Lint・ビルドを通す。機能追加・振る舞いの変更はテスト先行を必須とし、対象の振る舞いによる失敗を確認してから実装する。関数ごとの細かなサイクルは任意。振る舞いを変えないリファクタリングは変更前後のテスト成功で確かめる。不具合修正では原則として失敗する再現テストを先に作る。モックは必要な境界に絞り、実物の部品と計算を組み合わせて確かめる
- Playwright 導入後は、変更に関係する重要な操作フローも E2E で確かめる。環境と CI の導入は別 Issue で行い、未導入なのに確認済みと書かない
- ミューテーションテスト導入後は、[testing.md 7章](testing.md#7-ミューテーションテスト)の対象変更で、通常テストの成功後に実行する。生き残った変異を分類し、テストの補強と再確認を行い、判断・残件をレビューとふりかえりへ引き継ぐ。基盤の初期導入は専用Issueで行う
- PRを作る。本文には「何をしたか」「テスト結果」「確認したいこと」が入る
- 画面を含む変更では、操作できるブラウザまたは iOS シミュレーターで幅375pxとPCの表示・操作を確認し、環境・画面幅・確認手順・結果を PR に書く。確認できなかった項目と理由は明記する。DOM のテストだけで画面確認済みとはしない。スマホ実機での確認はステップ6で人間が行う
- GitHub Actions（CI）が自動で、テスト・型チェック・Lint・ビルドを回す
- 相棒はこの間、待っていればいい（スマホのOrcaアプリで完了通知を受け取ることもできる）

### ステップ6：レビュー【開発チーム・PO】
Orcaで差分を見る。エージェントのコードレビューでは、Issue・仕様・PR 本文に加えて、実コードとテスト、影響する呼び出し元・依存先も読む。対象コミットを記録し、修正後は更新差分と影響範囲を再確認する（詳しくは [テストとレビューの方針](testing.md)）。見るポイントは次のとおり：
- [ ] 受け入れ条件のチェックボックスが全部満たされているか
- [ ] CIが通っているか
- [ ] 実際に動かして触ってみる（Orcaには、作業場所ごとにブラウザで画面を確認できる機能がある）
- [ ] 画面を含む変更では、人間が同じ LAN のスマホ実機で開き、全体の見え方・座標ラベルの読みやすさ・指での操作と誤タップのしやすさを確認し、結果をレビューに残す。エージェントの幅375px確認と実機確認を区別する

問題があれば：
- 気になる行にコメントを付け、まとめてエージェントに返す → エージェントが直す
- 大きめのPRなら、Codexにもレビューさせる（別の会社のAIの目を入れる）

**任意：2つのエージェントで作らせて比べる**
- 同じIssueを、Claude CodeとCodexでそれぞれ実装させてもよい（worktreeを2つ作る）
- 比べると、spec.mdの抜けや、両方に足りない点が見つかりやすい（#1では「スマホ実機で開けるか」の差から、spec.mdの抜けが見つかった）
- 採用しないPRは、理由をコメントに残して閉じる
- 受け入れ条件を満たすための修正は、その PR で直して再確認する。独立した改善は別の Issue にする（1つの PR は1つの Issue だけ）
- 相互レビューは受け入れ条件・仕様・回帰の確認を担当し、必須チェックと主要な画面操作を再確認する。実行できない項目は理由と未確認範囲を残す
- #8・#9 では、さらに独立した品質担当を PR ごとの別セッションで試す。相互レビューと同じ SHA を別 worktree で読み、責務・状態・依存関係・変更のしやすさ・テストの有効性を確認する。空き枠の範囲で相互レビューと並行して進める
- コーディネーターが両レビューの指摘を裏付け、重複と誤検出を整理する。試行の有効な独自指摘・誤検出・所要時間を Issue レポートに残し、継続するかは #8・#9 の結果から判断する。他の Issue への追加は明示的に指定する
- ③〜⑥をまとめて回すスキルがある：Orcaのターミナル（mainのworktree）で `/dual-implement 番号`（Codexなら `$dual-implement 番号`。自動では呼ばれないので、名前を付けて呼ぶ）。途中で止まるのは④の計画承認と、最後の報告の2回だけ。マージ（⑦）は人間がする
  - 推薦する PR が決まると、開発チームが PO に受け入れの一次判断を頼む（`accept-review`）。PO はコードではなく、受け入れ条件・仕様・スコープ・使う人から見た振る舞いを見て、PR にコメントする。差し戻しなら開発チームが直して再確認し、受け入れか人間の判断が必要になった時点で人間に報告が来る
  - コーディネーターのモデル：Claude Code は `claude --model opus --effort high` で起動する。Codex は既定（`~/.codex/config.toml` の `gpt-6.1-sol`・high）のまま起動する。ワーカーのモデルは dual-implement の「モデルの指定」に従う

### ステップ7：マージ【開発チーム】
- [ ] PRをmainにマージする（`Closes #12` の効果でIssueが自動で閉じる）
- [ ] 採用判断に使うレビューと CI が現在の PR の head に対応し、必須指摘が解消されている。古いレビューの後で修正された場合は再確認する
- ⑦〜⑧を回すスキルがある：コーディネーターに `/finish-issue 採用するPR番号`（Codexなら `$finish-issue 番号`）。マージ・不採用PRのクローズ・後片付けに続けて、ふりかえりの結果と改善案を共有する。スキル・文書の修正や後続Issueの登録・更新は具体案への承認後に行う。同じ内容が既に具体的に承認されていれば再確認せず進めるが、マージ・後片付けの承認を新たな改善への包括的な承認とは扱わない
- [ ] [保存方法](issue-reports/README.md)に従って `docs/issue-reports/issue-番号.md` にマージ・後片付けの結果を記録し、ステップ8へ引き継ぐ。計画や検証の記録は worktree を消す前に集め、ふりかえり後に関連する改善をまとめて保存する。next-issues.md に載せる内容は PO へ申し送る。finish-issue を使う場合は同スキルが担当する
- [ ] 他のIssueを並行して進めている場合は、そちらの作業場所をmainの最新に合わせる

### ステップ8：ふりかえりと還流【開発チーム（finish-issue）／PO】★ここがサイクルの要
完成したものと検証・レビューの記録から、続けること・改善すること・まだ判断できないことを整理し、レポートへのリンクだけでなく会話で結果を共有する。改善案ごとに根拠・反映先・具体的な変更内容・期待する効果と確認方法を示し、人間に採否を確認する。`finish-issue` では、承認された改善を反映して結果を報告する。具体的な手順は[finish-issue](../.claude/skills/finish-issue/SKILL.md)に従う。

分かったことを次の種類に振り分ける：

| 気づきの種類 | 戻す先 | 例 |
|---|---|---|
| 仕様についての発見 | `docs/spec.md`（PO へ申し送り、PO が反映） | 「キャラが4体だとタップしにくい」→ 盤面サイズを見直す |
| エージェントの失敗の傾向 | `CLAUDE.md`・`AGENTS.md` または共通のスキル | 「毎回テストを書き忘れる」→ 手順書に1行足す |
| 実装・テストの改善 | 後続 Issue、または実装スキルの参考観点 | 「共通型を整理する」→ 小さな別 Issue。「境界と期待一覧を確認する」→ 関連する計算のテスト計画で検討 |
| 開発環境・運用の改善 | 関連文書・補助スクリプト・設定、または後続 Issue | 既に消えたworktreeの扱いを後片付け手順に追記する |
| 物語になる出来事 | Issue レポート。vaultのネタ帳への転記は利用者が行う | 「ClaudeとCodexで距離計算の解き方が違った」 |

既存のルールやIssueを確認し、今回の根拠がある改善だけを提案する。スキル・文書・設定の修正やIssueの登録・更新は、人間が採用した具体案の範囲で行う。従来の方針に沿うことだけでは、新しい改善案への承認とは扱わない。返答待ちの改善は反映せず、完了した作業の事実と改善案を「判断待ち」としてレポートへ保存できる。独立したアプリの実装は後続Issueで行う。候補がなければ、改善不要と判断した理由を残す。

前回の改善は、今回試した場面・証拠・結果から「効果を観測／問題が再発／未確認（対象場面なし・証拠不足など）」を記録する。「手順に反映済み」と「効果を確認済み」を分け、継続・修正・削除・継続観測を判断する。次のIssueで試す改善は関連するものに絞り、確認担当と時点を引き継ぐ。

新しい改善候補には、人間の判断として採用（反映先・担当・確認時点）、見送り（理由）、保留・条件付きで再検討（条件・担当）のいずれかを残す。採否が未決なら判断待ちと明記し、判断する人と確認を求めた時点を残す。#9のふりかえりでは、[testing.mdの評価方法](testing.md#二重実装と品質レビューの評価)に従い、#8・#9を通した二重実装と独立した品質レビューの継続方針を利用者に示す。

チェック：
- [ ] ふりかえりの結果と具体的な改善案を会話で共有した
- [ ] 改善案の採否を人間に確認し、承認された範囲をそれぞれの戻す先に反映した。判断待ちの案は反映せず、状態を記録した
- [ ] 次のステップ1の議題が決まった
- [ ] 前回の改善の効果と、今回の候補の採否・次に確認する担当と時点を記録した
- [ ] Issue レポートに、改善の反映先へのリンクと「反映済み／登録済み・未実装／判断待ち／見送り」などの状態を追記し、保存した。未実装の改善を完了と書かない
- [ ] 実際に反映した改善と検証結果、残した課題を人間に報告した

→ ステップ1に戻る。

## 具体例：距離計算のIssueで一周すると

1. **議論**：「斜めは1→2と交互に数える」と決まる → spec.mdの「3. ルールの扱い」に書く
2. **切り出し**：Issue「距離と移動範囲の計算」を作る。受け入れ条件に「(0,0)→(4,4)は6」などの表、スコープ外に「画面表示」
3. **着手**：Orcaで選んで `/implement-issue 3`
4. **計画承認**：エージェントが「他キャラのマスを通り抜けられるかが不明です」と聞いてくる → spec.mdの未決事項にある話なので、「今回は止まれないマスを除くだけ」と答えて承認
5. **実装**：テストが全部通った状態でPRが届く
6. **レビュー**：差分とテスト結果を見て、OK
7. **マージ**：Issueが自動で閉じる
8. **還流**：「すり抜けは、画面で触る前に決めたほうがいい」と気づく → 次のステップ1の議題にする

## 迷ったときの判断基準

| 迷い | 判断 |
|---|---|
| spec.mdに書く？Issueに書く？ | 次のIssueが終わっても変わらない決めごと → **spec.md**。今回の作業範囲だけの話 → **Issue** |
| PO に戻すべき？ | エージェントに答えると**仕様を決めることになる**なら戻る。どちらでもいい実装上の選択なら、その場で答えてよい |
| Issueは何本先まで書く？ | **最大3本**。それより先は spec.md の「将来」に書くだけ |
| 並列で進めていい？ | 基本は1本ずつ。開発チームは同時に1つまでで、起動係もそれを守る。並行するときはスキルの改善を後回しにする |

## どこに何が残るか

| ファイル／場所 | 持つもの | 寿命 |
|---|---|---|
| `docs/spec.md` | 全体像・決定事項・未決事項 | ずっと育てる |
| `docs/testing.md` | テストとレビューの共通方針 | 実践の結果を見て育てる |
| Issue | 今やる一片の作業範囲 | マージで閉じる |
| PR | どう作ったか・レビューのやりとり | 記録として残る |
| `docs/issue-reports/issue-番号.md` | 1 Issue の計画・判断・検証・完了処理と改善の反映先 | 記録として残し、続きは同じファイルへ追記 |
| `CLAUDE.md` / `AGENTS.md` | エージェントの常識 | 失敗の傾向を見て育てる |
| `.git/po.handle`・`.git/dev-team.lock` | PO と動いている開発チームの端末（Git の管理外） | 開き直し・Issue ごとに書き換わる |
| `.claude/skills/` / `.agents/skills/` | 実装・レビュー・完了処理の手順（両方を同じ内容に保つ） | 実践の結果を見て育てる |
| vaultのネタ帳 | 開発の経緯（日記の素材） | 追記のみ |
