# 戦闘ボード開発の進め方（Spec × Issue × Orca）

仕様の全体像は `docs/spec.md` に持つ。そこから**今すぐ作る一片だけ**をIssueに切り出し、Orcaで1本ずつ実装する。

- `docs/spec.md` … アプリ全体の「何を・なぜ・どこまで」を持つ地図。まだ作らない部分も書いてよい
- Issue … 地図から今作る一片だけを切り出した作業票。1〜3本ずつ出し、終わったら次を切る
- [docs/testing.md](testing.md) … テストの層・TDD・モックとレビューの分担を決める共通方針
- [docs/issue-reports/](issue-reports/README.md) … 1 Issue につき1ファイルで、計画・承認・検証・採用理由・後片付け・改善の反映先を残す記録

---

## 登場する「場所」は2つ

| 場所 | 道具 | そこでやること |
|---|---|---|
| **設計の席** | Claude Codeアプリ（リポジトリのフォルダで起動し、vaultも参照先に追加） | 議論する、仕様を書く、Issueを切る、ふりかえる |
| **実装の席** | Orca（中でClaude CodeやCodexが動く） | Issueを1本ずつ実装する、PRを作る、レビューする |

ファイルの置き場所はGitHubのリポジトリ1つ。どちらの席も同じリポジトリを見ている。

## 最初に1回だけやる準備

### 準備1：設計の席を開く
- [ ] Claude Codeアプリで `~/orca/overstrata-board` を開く（`git@github.com:dyamada-jaki/overstrata-board.git`）
- [ ] vaultのフォルダを参照先に追加する（`git@github.com:dyamada-jaki/overstrata.git` → `~/Documents/obsidian/overstrata`）
  - vaultは**読むだけ**。アプリ側の都合で書き換えない。`20_gm_secret/` は読まない（→ [spec.md 3.0](spec.md)）

→ ルールや模擬戦ログを読みながら議論でき、`gh` でIssueも書ける。

### 準備2：仕様書の初版を作る
- [ ] これまでの決定事項を `docs/spec.md` にまとめる

構成の例：

```
1. このアプリは何か（音声プレイ中の戦闘ボード）
2. 画面と操作（盤面・キャラ・移動）
3. ルールの扱い（補助のみ／距離の数え方／移動力）
4. 今はやらないこと（地形・射程・保存…）
5. 未決事項（すり抜け可否など）
```

### 準備3：エージェント向けの2つのファイルを置く
- [ ] `CLAUDE.md`：エージェントの常識（コマンド・フォルダ構成・守ること）。**短く保つ**
- [ ] `AGENTS.md`：Codex用。`CLAUDE.md` と同じ内容
- [ ] `.claude/skills/implement-issue/SKILL.md`：Issueを実装するときの手順書。中身は次の5手順
  1. `gh issue view 番号` でIssueを読む
  2. `docs/spec.md` の該当箇所を読む
  3. 実装計画を出して、承認を待つ
  4. 実装してテストを通す
  5. テスト結果などの証拠を付けて、`Closes #番号` 入りのPRを作る

> **注意**：vaultには `20_gm_secret` がある。リポジトリが公開なら、spec.md・Issue・CLAUDE.md に秘匿要素を書かない。このルールも `CLAUDE.md` に入れておく。

### 準備4：mainにコミットする
- [ ] ここまでは**相棒が**mainにコミットする

→ 「エージェントの土台は人間が置く」という線引き。

## 毎回まわすサイクル（8ステップ）

```
① 議論 → ② 切り出し → ③ 着手 → ④ 計画承認 → ⑤ 実装 → ⑥ レビュー → ⑦ マージ → ⑧ ふりかえり ─┐
  ↑                                                                                   │
  └───────────────────────────────────────────────────────────────────────────────────┘
  （設計の席）      （設計の席）      （実装の席 ③〜⑦）                                   （設計の席）
```

### ステップ1：議論する【設計の席】
- **入力**：前回のふりかえりで出た気づき、または新しくやりたいこと
- **やること**：AIが相棒に質問して、決めるべき点を洗い出す
  - 例：「すり抜けはできる？」「前衛は動く壁って、敵の移動を止めるの？」
- **出力**：`docs/spec.md` の更新。決まったことを書き足し、未決事項から消す
- **なぜ**：全体像を1か所に保つため。会話は消えるけど、spec.mdは残る

チェック：
- [ ] 決まったことを spec.md に書いた
- [ ] 未決事項の一覧を更新した
- [ ] mainにコミットした

### ステップ2：Issueを切り出す【設計の席】
- **やること**：spec.mdの中から「今すぐ作る一片」を1〜3本選ぶ
- **選ぶ基準**（3つとも満たすもの）
  1. 前提がそろっている（依存しているものが完成済み）
  2. PR1本で終わる大きさ
  3. 完成したかどうかを確かめられる（テスト、または画面で見て分かる）
- **区切り1の先行登録（2026-10-14）**：利用者の希望により、区切り1の残りはまとめて登録する。依存先が未完了でも登録できるが、Issue の「前提・着手条件」に依存先と未決事項を明記する。基準1は実装に着手する時点で満たすこと。未決の仕様は着手前に spec.md へ反映する。PR1本の大きさと確認可能な受け入れ条件は、先行登録でも維持する
- **Issueに書くこと**
  - 目的（1〜2行）
  - spec.mdの該当箇所へのリンク
  - 受け入れ条件（チェックボックス）
  - スコープ外（やらないこと）
  - 画面がある場合、エージェントの確認と人間の実機レビューを分けて記載する。実機での操作をエージェントの PR 作成条件にしない
- **Issueに書かないこと**
  - 関数名やファイル構成などの実装方法 → エージェントがステップ4で自分で考える
- **出力**：AIが `gh issue create` でGitHubに登録する
- **なぜ短く保つか**：詳しい内容はspec.mdにある。Issueに写すと二重管理になって、片方だけが古くなる

チェック：
- [ ] 選んだIssueが3つの基準を満たしている
- [ ] Issueにspec.mdへのリンクがある
- [ ] 受け入れ条件とスコープ外が書いてある
- [ ] GitHubに登録された

### ステップ3：着手する【実装の席】
- [ ] Orcaを開き、登録したIssueを一覧から選ぶ
- [ ] worktreeを作る（そのIssue専用の作業場所ができる）
- [ ] エージェントを選ぶ（まずはClaude Code）
- [ ] エージェントに1行だけ打つ：`/implement-issue 12`

**なぜ1行で済むか**：手順はスキルに、仕様はspec.mdに、作業範囲はIssueに書いてあるから。毎回長い指示を書かなくていい。

### ステップ4：計画を承認する【実装の席】★ここが関所
エージェントは、すぐにはコードを書かない。まず「こう作ります」という計画を出してくる。

相棒はIssueと見比べて確認する：
- [ ] 受け入れ条件を全部カバーしているか
- [ ] 仕様から期待結果を決め、各条件をどの層のテスト・画面確認で確かめるかが明確か（[テスト方針](testing.md)）
- [ ] スコープ外のことをやろうとしていないか
- [ ] エージェントが「確認したいこと」を挙げていないか

**分岐**：
- 計画が妥当 → 承認してステップ5へ
- 小さな疑問 → その場で答える
- 仕様の穴が見つかった → **実装を止めて設計の席に戻る**。spec.mdとIssueを直してからやり直す

**なぜここが関所か**：Issueの曖昧さは計画に表れる。コードになる前に見つけるのがいちばん安い。

承認した計画の要点と、確認事項の決着を控える。通常の実装では PR 本文に、dual-implement ではコーディネーターのレポートに残し、後から承認内容を追えるようにする。

### ステップ5：実装【実装の席・エージェントが自走】
- [テスト方針](testing.md)に従って実装し、テスト・型チェック・Lint・ビルドを通す。細かな TDD は任意。不具合修正では原則として失敗する再現テストを先に作る。モックは必要な境界に絞り、実物の部品と計算を組み合わせて確かめる
- Playwright 導入後は、変更に関係する重要な操作フローも E2E で確かめる。環境と CI の導入は別 Issue で行い、未導入なのに確認済みと書かない
- PRを作る。本文には「何をしたか」「テスト結果」「確認したいこと」が入る
- 画面を含む変更では、操作できるブラウザまたは iOS シミュレーターで幅375pxとPCの表示・操作を確認し、環境・画面幅・確認手順・結果を PR に書く。確認できなかった項目と理由は明記する。DOM のテストだけで画面確認済みとはしない。スマホ実機での確認はステップ6で人間が行う
- GitHub Actions（CI）が自動で、テスト・型チェック・Lint・ビルドを回す
- 相棒はこの間、待っていればいい（スマホのOrcaアプリで完了通知を受け取ることもできる）

### ステップ6：レビュー【実装の席】
Orcaで差分を見る。エージェントのコードレビューでは、Issue・仕様・PR 本文に加えて、実コードとテスト、影響する呼び出し元・依存先も読む。対象コミットを記録し、修正後は更新差分と影響範囲を再確認する（詳しくは [テストとレビューの方針](testing.md)）。見るポイントは次のとおり：
- [ ] 受け入れ条件のチェックボックスが全部満たされているか
- [ ] CIが通っているか
- [ ] 実際に動かして触ってみる（Orcaには、作業場所ごとにブラウザで画面を確認できる機能がある）
- [ ] 画面を含む変更では、人間が同じ LAN のスマホ実機で開き、全体の見え方・座標ラベルの読みやすさ・指での操作と誤タップのしやすさを確認し、結果をレビューに残す。エージェントの幅375px確認と実機確認を区別する

問題があれば：
- 気になる行にコメントを付け、まとめてエージェントに返す → エージェントが直す
- 大きめのPRなら、Codexにもレビューさせる（別の会社のAIの目を入れる）

**任意：2つのエージェントで作らせて比べる**
- 同じIssueを、Claude CodeとCodexでそれぞれ実装させてもよい（worktreeを2つ作る）
- 比べると、spec.mdの抜けや、両方に足りない点が見つかりやすい（#1では「スマホ実機で開けるか」の差から、spec.mdの抜けが見つかった）
- 採用しないPRは、理由をコメントに残して閉じる
- 受け入れ条件を満たすための修正は、その PR で直して再確認する。独立した改善は別の Issue にする（1つの PR は1つの Issue だけ）
- 相互レビューは受け入れ条件・仕様・回帰の確認を担当し、必須チェックと主要な画面操作を再確認する。実行できない項目は理由と未確認範囲を残す
- #8・#9 では、さらに独立した品質担当を PR ごとの別セッションで試す。相互レビューと同じ SHA を別 worktree で読み、責務・状態・依存関係・変更のしやすさ・テストの有効性を確認する。空き枠の範囲で相互レビューと並行して進める
- コーディネーターが両レビューの指摘を裏付け、重複と誤検出を整理する。試行の有効な独自指摘・誤検出・所要時間を Issue レポートに残し、継続するかは #8・#9 の結果から判断する。他の Issue への追加は明示的に指定する
- ③〜⑥をまとめて回すスキルがある：Orcaのターミナル（mainのworktree）で `/dual-implement 番号`（Codexなら `$dual-implement 番号`。自動では呼ばれないので、名前を付けて呼ぶ）。途中で止まるのは④の計画承認と、最後の報告の2回だけ。マージ（⑦）は人間がする
  - コーディネーターのモデル：Claude Code は `claude --model opus --effort high` で起動する。Codex は既定（`~/.codex/config.toml` の `gpt-6.1-sol`・high）のまま起動する。ワーカーのモデルは dual-implement の「モデルの指定」に従う

### ステップ7：マージ【実装の席】
- [ ] PRをmainにマージする（`Closes #12` の効果でIssueが自動で閉じる）
- [ ] 採用判断に使うレビューと CI が現在の PR の head に対応し、必須指摘が解消されている。古いレビューの後で修正された場合は再確認する
- マージから後片付けまでを回すスキルがある：コーディネーターに `/finish-issue 採用するPR番号`（Codexなら `$finish-issue 番号`）。採らないPRを理由付きで閉じ、worktree・Dockerのコンテナとボリュームを消す。実行前に1回だけ確認を求める
- [ ] [保存方法](issue-reports/README.md)に従って `docs/issue-reports/issue-番号.md` を完成させ、next-issues.md と一緒に保存する。計画や検証の記録は worktree を消す前に集める。finish-issue を使う場合は同スキルが担当する
- [ ] 他のIssueを並行して進めている場合は、そちらの作業場所をmainの最新に合わせる

### ステップ8：ふりかえりと還流【設計の席】★ここがサイクルの要
完成したものを見て、分かったことを次の種類に振り分ける：

| 気づきの種類 | 戻す先 | 例 |
|---|---|---|
| 仕様についての発見 | `docs/spec.md` | 「キャラが4体だとタップしにくい」→ 盤面サイズを見直す |
| エージェントの失敗の傾向 | `CLAUDE.md` またはスキル | 「毎回テストを書き忘れる」→ 手順書に1行足す |
| 実装・テストの改善 | 後続 Issue、または実装スキルの参考観点 | 「共通型を整理する」→ 小さな別 Issue。「境界と期待一覧を確認する」→ 関連する計算のテスト計画で検討 |
| 物語になる出来事 | vaultのネタ帳（【制作】） | 「ClaudeとCodexで距離計算の解き方が違った」 |

チェック：
- [ ] 気づきの種類に応じて、それぞれの戻す先に書いた
- [ ] 次のステップ1の議題が決まった
- [ ] Issue レポートに、改善の反映先へのリンクと対応状態を追記した。未実装の改善を完了と書かない

→ ステップ1に戻る。

## 具体例：距離計算のIssueで一周すると

1. **議論**：「斜めは1→2と交互に数える」と決まる → spec.mdの「3. ルールの扱い」に書く
2. **切り出し**：Issue「距離と移動範囲の計算」を作る。受け入れ条件に「(0,0)→(4,4)は6」などの表、スコープ外に「画面表示」
3. **着手**：Orcaで選んで `/implement-issue 3`
4. **計画承認**：エージェントが「他キャラのマスを通り抜けられるかが不明です」と聞いてくる → spec.mdの未決事項にある話なので、「今回は止まれないマスを除くだけ」と答えて承認
5. **実装**：テストが全部通った状態でPRが届く
6. **レビュー**：差分とテスト結果を見て、OK
7. **マージ**：Issueが自動で閉じる
8. **還流**：「すり抜けは、画面で触る前に決めたほうがいい」と気づく → 次のステップ1の議題にする

## 迷ったときの判断基準

| 迷い | 判断 |
|---|---|
| spec.mdに書く？Issueに書く？ | 次のIssueが終わっても変わらない決めごと → **spec.md**。今回の作業範囲だけの話 → **Issue** |
| 設計の席に戻るべき？ | エージェントに答えると**仕様を決めることになる**なら戻る。どちらでもいい実装上の選択なら、その場で答えてよい |
| Issueは何本先まで書く？ | **最大3本**。それより先は spec.md の「将来」に書くだけ |
| 並列で進めていい？ | 依存のない小さなIssue同士ならOK。最初は1本ずつで流れに慣れる |

## どこに何が残るか

| ファイル／場所 | 持つもの | 寿命 |
|---|---|---|
| `docs/spec.md` | 全体像・決定事項・未決事項 | ずっと育てる |
| `docs/testing.md` | テストとレビューの共通方針 | 実践の結果を見て育てる |
| Issue | 今やる一片の作業範囲 | マージで閉じる |
| PR | どう作ったか・レビューのやりとり | 記録として残る |
| `docs/issue-reports/issue-番号.md` | 1 Issue の計画・判断・検証・完了処理と改善の反映先 | 記録として残し、続きは同じファイルへ追記 |
| `CLAUDE.md` / `AGENTS.md` | エージェントの常識 | 失敗の傾向を見て育てる |
| `.claude/skills/` / `.agents/skills/` | 実装・レビュー・完了処理の手順（両方を同じ内容に保つ） | 実践の結果を見て育てる |
| vaultのネタ帳 | 開発の経緯（日記の素材） | 追記のみ |
