## 2. 目的と範囲

CI のミューテーションテストの待ち時間を短くする。(1) CI だけ並列数を上げる（手元の既定2は維持）、(2) Markdown だけの変更ではミューテーションを省く。変異対象・型チェック・判定条件は変えない。E1〜E4（旧サンプル整理・`ignoreStatic`・incremental・ジョブ分割）はスコープ外で保留。

### 実装中の判断（コーディネーター、2026-10-25 21:19〜21:22 JST）

並列数4の実測で Timeout が4件から52〜66件に増え（Survived・Killed が Timeout に変わる）、時間も短くならなかった。両ワーカーがそれぞれ独立に計画変更を相談した（Codex 21:19、Claude Code 21:22 JST）。受け入れ条件7「効果が見えない・不安定なら、並列数を増やしただけで完了とせず、結果と次の判断材料を報告する」の範囲の判断として、コーディネーターが次のように答えた（人間には最終報告で伝える）。

- CI の並列数は2を明示し、環境変数の仕組みとプロセス数の確認は残す。4の2回分の結果を PR に記録する
- 並列数3は測らない（Stryker は checker ceil(3/2)=2・test runner floor(3/2)=1 に割り当て、test runner が増えないため）。6も承認の条件を満たさないため測らない
- Timeout の判定条件（`timeoutMS`・`timeoutFactor`）は変えない（スコープ外「検出条件の緩和」）
- Markdown 省略の実例は、採用値2の全対象成功を比較元にして取り直す

### ADR の候補（finish-issue で判断）

- 「CI のミューテーションは、全対象で成功した run が実際に検証したツリーからの差分が Markdown だけのときに限り省略する。判定できなければ実行する」
- 「並列数は CI だけ環境変数で指定し、手元は2。CPU 4 の CI では4にしても短くならず Timeout が増えた」
- 2案で違った点：検証済みの記録の持ち方（step の成功だけか、検証した SHA 入りの artifact か）。今回の相互レビューで、head の SHA だけでは検証したマージ結果と結び付かないことが分かった（6章）
