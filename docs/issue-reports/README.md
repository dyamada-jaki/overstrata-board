# Issue 対応レポート

1つの Issue について、仕様からの切り出し・計画承認・実装・検証・レビュー・採用判断・後片付けまでを、1つのファイルに残す。
仕様の正本は [spec.md](../spec.md)、現在の作業範囲は GitHub Issue に置く。レポートは、その時点で何を根拠に判断したかを振り返るための記録とする。

## 保存方法

- ファイル名は `issue-番号.md`（例: `issue-7.md`）。同じ Issue の続きは同じファイルを更新する。
- 複数のエージェント・PR で比較した場合も1ファイルにまとめる。
- 日時を書く場合はタイムゾーンを明記する。このリポジトリでは日本時間（JST）を使う。
- 過去の対応をまとめる場合、残っている Issue・PR・CI・会話から確認できることだけを書く。欠けた計画・承認・実行結果は「記録なし」「未確認」とする。
- 最新の仕様を過去の実装時点へさかのぼって適用しない。必要なら当時のコミットへのリンクを付ける。
- GM 向けの秘匿情報、認証情報、環境変数の秘密の値は記載しない。

## 保存するタイミングと担当

| タイミング | 担当・残すこと |
|---|---|
| 計画承認〜PR 作成 | 実装者が、承認した計画の要点・確認事項と決着を PR 本文に残す。dual-implement ではコーディネーターが両者の計画と承認を控える |
| 比較・レビューの報告 | dual-implement のコーディネーターが main の作業場所でレポートを作成・更新する。採用前は「採用待ち」と明記し、ワーカーには同じファイルを編集させない |
| PO の受け入れ確認 | dual-implement のコーディネーター（開発チーム）が、PO の判定・回数・対象 SHA・差し戻しで直した内容と再確認を追記する。PO はレポートを編集せず、判定を PR コメントに残す |
| マージ・後片付け | finish-issue の担当者が、削除前に必要な記録を集め、採用結果・後片付け・残課題を確定し、ふりかえりへ進む |
| ふりかえり・改善の反映 | finish-issue の担当者が結果と具体的な改善案を会話で示し、人間に採否を確認する。承認された改善を反映し、人間の判断・反映先の文書やスキル・Issue へのリンクと「反映済み／登録済み・未実装／判断待ち／見送り」などの状態を同じファイルに追記する。返答待ちでも完了した作業の事実と改善案は保存できる。next-issues.md と関連する変更を main へコミット・push し、結果を報告する。後日、設計の席で決めた内容も同じファイルに追記する |

finish-issue を使わない場合も、マージ担当者が同じ記録を残す。未完了で終える場合は未完了の状態と残作業を記し、完了としない。

## レポートに含める内容

Issue の大きさに合わせて短くまとめ、次を確認できるようにする。

1. **概要**: Issue・期間・採用 PR・不採用 PR・仕様の参照先。実装・自動検証、main取り込み、人間の実機確認、区切りの達成を分けて記録する（workflow.md「Issueと区切りの確認」）。
2. **目的と範囲**: 何ができるようになるか、前提、スコープ外。
3. **進行と人間の判断**: 計画、確認事項、承認内容、採用・後片付けの判断。分かる範囲の日時と根拠。
4. **実装の比較**: 作りの違いと、その影響。単独実装なら比較は不要。
5. **受け入れ条件と検証**: 条件ごとの判定と根拠、テスト・CI・画面・実機の確認結果。実行環境と対象コミット。E2E・ミューテーションテストは結果または未実施／対象外の理由を記す。ミューテーションの対象・状態別結果・生き残った変異の判断と対応先は testing.md 7章に従う。
6. **レビューと採用理由**: 相互レビューと品質レビューを区別し、担当・対象 SHA・コメントへのリンク・読んだ範囲・実行した確認を残す。指摘の重さ、コーディネーターが裏付けたこと、採用理由、修正後の再確認・保留の扱い。
7. **完了処理**: マージ、Issue・PR の状態、削除した資源と残した資源、できなかったこと。
8. **学びと次の作業**: 仕様の発見、今回観察した実装の違い、改善の反映先と状態、残る未決事項。前回の改善を試した場面・証拠・効果または未確認の理由を残し、反映済みと効果確認済みを分ける。新しい改善への人間の採用・見送り・保留の判断と再検討条件、次に確認する担当・時点を記す。未回答は判断待ちとし、承認されたことにしない。

作成者の実行報告、レビュー担当者の再確認、コーディネーターの確認を区別する。CI・レビューコメント・重要なコミットにはリンクを付ける。1回の比較だけでモデル全般の優劣や速さを断定せず、テスト件数だけで品質を評価しない。

[テストとレビューの方針](../testing.md)に沿って、#8・#9 の品質レビューの試行では、相互レビューと重複しなかった有効な指摘・誤検出と除外理由・担当別の所要時間と全体の追加待ち時間を残す。測れなければ「記録なし」とする。品質レビューをしなかった Issue に、実施したかのような記録を加えない。

二重実装の比較と品質レビューの追加価値を区別し、具体的な採用先・修正後の確認・残件・誤検出による手戻りを残す。#9のふりかえりで#8・#9を比較し、担当構成の継続案と利用者の判断を同じレポートに記録する。

レビュー専用の worktree がある場合は、対象 PR・対象 SHA・パス・ローカルブランチ・dispatch ID・使用した Docker 資源を記録し、finish-issue で削除対象を照合できるようにする。
