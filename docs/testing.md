# テストとレビューの方針

アプリの振る舞いの正本は [spec.md](spec.md)、今回の範囲は GitHub Issue に置く。この文書は、仕様をどう確かめ、変更をどうレビューするかを決める。Codex と Claude Code は同じ方針を使う。

## 1. 実装前に決めること

- 受け入れ条件ごとに、入力・操作・期待結果と、確かめる層を計画に書く。期待結果は仕様から決め、実装の出力をそのまま正解にしない。
- 正常な例だけでなく、境界、選択の切り替え、操作しても変わらない場合など、その変更で間違えやすい点を選ぶ。仕様にない入力制約やゲームのルールはテストにも追加しない。
- **機能追加・振る舞いの変更では、テストを先に書いてから実装する（テストファースト）。** 計画で決めたテストを実装より先に書いて実行し、**対象の振る舞いが未実装、または誤っているために失敗する**ことを確かめる。期待値と結果の不一致だけでなく、未実装の画面要素が見つからないことも含む。環境設定の不備や無関係な import・型エラーは、対象の振る舞いを検証できた証拠にしない（関数や部品の空の枠だけ先に作ってよい）。そのテストを実装より前のコミットにし、そのあと実装して通す。PR のコミット履歴と本文で、この順番が分かるようにする。
  - 単位は受け入れ条件（振る舞い）ごとでよい。関数ごとの細かな Red → Green → Refactor の繰り返しまでは求めない。計算や状態遷移で役立つなら使う。
  - 実装中に必要と分かったテストは追加してよい。ただし、先に書いたテストを実装に合わせて弱めない。
  - 振る舞いを変えないリファクタリングでは、既存テストが変更前後で通ることを確かめる。既存テストが不足していれば、変更前に現在の振る舞いを確認するテストを追加して通す。新しく失敗するテストを作る必要はない。
  - 対象外：テストで確かめる振る舞いのない変更（文書・設定・依存の更新など）。E2E は先に書けるなら先に書き、環境の都合で書けない場合は実装と同時でよい。
  - 先に書けなかったテストがあれば、理由を PR に書く。
- アプリの不具合修正では、原則として修正前に失敗する再現テストを作り、修正後に通ることを確かめる。実機だけで起きるなど自動化できない場合は、再現手順・修正前後の結果・自動化できない理由を PR に残す。
- 期待値や検証条件を変えるときは、根拠となる仕様または元のテストの誤りを説明する。通すためだけに assertion を減らしたり、失敗するテストを無効化したりしない。

## 2. テストの層と分担

振る舞いは**処理の入り口**で確かめるのを中心にする。細かな関数ごとのテストは、下の条件に当たるものだけに書く。

| 層 | 位置づけ | 主に確かめること | 書き方 |
|---|---|---|---|
| Vitest + React Testing Library：画面操作の結合 | **主役** | 画面から呼ばれる入り口。操作に対する表示・選択・状態の変化 | 実際の部品・状態管理・domain 関数を組み合わせ、利用者が見える表示や結果を確かめる。内部関数の呼び出し方に依存しない |
| Vitest：domain | **条件付き** | 次のどれかに当たる計算。①仕様に例や表があるルール（距離・移動力など）②分岐や境界が多く、画面からでは組み合わせを試しにくい処理 ③複数の画面から使われる処理 | 外から使われる関数を基本の単位にする。内部の補助関数の個別テストは必須にせず、複雑な計算や境界条件を効果的に確かめられる場合に追加する。仕様の例、境界の内外、必要な対称性、入力を変更しないことを選ぶ。一覧は小さな例の期待一覧で欠落・混入も確かめる。条件に当たらない単純な処理は、画面操作のテストで確かめれば足りる |
| Playwright：E2E | **仕上げ** | 配信されたアプリを実ブラウザで開いた一連の操作 | 重要な流れを少数に絞る。細かい入力の組み合わせは下の層で確かめ、同じ組み合わせを網羅し直さない |
| エージェントによる画面確認 | **自動テストの補完** | 幅375pxとPCの表示・操作、ラベルや選択の見分けやすさ | ブラウザまたはシミュレーターで確認し、環境・幅・操作・結果を残す。DOM テストだけで確認済みとはしない |
| 人間による実機確認 | **使い勝手の確認** | 指での操作、誤タップのしやすさ、実際の読みやすさ | レビュー時にスマホで確かめる。ブラウザの端末エミュレーションとは区別する |

将来バックエンドを導入したら、**API の入り口**を主役にする（隔離した実物の DB などを使った結合テスト）。複雑な処理は上の domain と同じ条件で単体テストを書き、画面からの一連の流れは E2E で確かめる。

一覧を返す計算の具体例は [Issue #7 のレポート](issue-reports/issue-7.md)を参照する。テスト件数やカバレッジの数値だけで品質を判断しない。各テストが「どの誤りを見つけるか」を説明できることを重視する。単なる文言や書式の変更に、実装をなぞるだけのテストを増やさない。

## 3. モックは必要な境界だけに使う

**古典派を基本にし、実物を使った結果の検証を優先する。** 純粋関数、React の部品、アプリ内の状態管理を、それぞれモックに置き換えて結合を失わないようにする。

- 外部サービス、時刻、乱数など、遅い・不安定・副作用がある境界では、stub・fake・mock を使ってよい。使う理由と、実物との接続をどこで確かめるかを計画と PR に書く。
- 呼び出し回数や内部の手順より、戻り値・表示・保存された状態などの結果を検証する。外部送信の重複防止など、呼び出し自体が契約になる場合は、その理由を明示して検証する。
- テストごとに状態を独立させる。実物を使う場合も、本番データや実際の外部送信先を使わない。将来サーバーや DB を導入したときは、可能な範囲で隔離した実物のテスト環境を使う。
- スナップショットだけで操作や計算の正しさを判断しない。利用者が観察できる結果を明示して確かめる。

## 4. Playwright の導入と対象

[#13](https://github.com/dyamada-jaki/overstrata-board/issues/13)で Playwright を導入。現在の最小テストは、Docker で配信した実際のアプリを Chromium の375×667px・1280×720pxで開き、見出しと未処理の JavaScript 例外がないことを確認する。main へ取り込んでから #8 → #9 の順で進め、操作 E2E は各機能と同じ Issue・PR に含める。

[README の E2E 手順](../README.md#e2eplaywright)に従い、Docker のみなら `sh scripts/e2e.sh --docker`、ホストに Node 24 と Chromium を準備した場合は `npm run test:e2e` で実行する。どちらも現在の checkout の本番アプリコンテナを新規作成し、準備完了を待って検証し、終了時にその実行の資源だけ片付ける。Docker runner 内でも同じ npm コマンドを使うが、コンテナの再帰起動は行わない。

既存の `test` / `typecheck` / `lint` / `build` に加え、#13 自体と対象となる UI 変更では E2E の成功も必須とする。Vitest は `src/`、Playwright は `e2e/` を収集し、後者も型チェック・Lint の対象とする。結果は実行ごとの `e2e-artifacts/run-*/` に残し、失敗時の HTML report・trace・スクリーンショット・アプリログを調べる。CI は同じ Docker 手順を実行し、成功・失敗にかかわらず artifact を保存する。再試行は0回とし、一度の失敗を失敗として扱う。

UI を変更する Issue では、次のような重要な流れを追加・更新する。環境がまだ無く、Issue で E2E を要求していない場合は RTL とブラウザで確認し、E2E 化は未実施として後続作業に残す。#8・#9 のように E2E を必須とする Issue では、環境の導入が着手条件になる。

- #8 の流れ：盤面を開く → マスを選ぶ → 別のマスへ切り替える → 同じマスで解除する。幅375pxで横スクロールが出ないことも確認する。
- #9 の流れ：キャラを選ぶ → 範囲が出る → 空きマスへ移動する → 選択と範囲が消える。別キャラのタップでは移動せず選択が切り替わること、範囲外の空きマスにも移動できることを含める。

E2E は実際のアプリと domain 処理を使う。要素は role や表示名を優先して特定し、必要な場合だけ安定した test ID を使う。固定時間の待機ではなく、期待する状態を待つ。失敗時はログ・trace 等の調査材料を残し、再試行で通っただけの不安定なテストを正常と扱わない。ブラウザの375px確認で、人間の実機確認を済ませたことにはしない。

## 5. PR レビューの分担

レビュー対象は PR の説明や差分だけではない。Issue・仕様を起点に、**変更された実コードとテスト、その呼び出し元・依存先・関連する既存テスト**まで、影響を判断できる範囲で読む。無関係な箇所まで全リポジトリを精査することは求めない。

| 担当 | 主な責任 |
|---|---|
| 相互レビュー担当 | 受け入れ条件を1つずつ判定し、仕様との一致、バグ・回帰、スコープ、検証の証拠を確認する。対象コミットで必須チェックを再実行する。UI では変更に関係する主要操作もブラウザで確かめる |
| 独立した品質レビュー担当 | 新しいセッションで、責務の分け方、状態の重複・同期、依存の向き、型や境界の扱い、過剰な抽象化、変更のしやすさ、テストが誤りを捕まえるかを確認する |
| コーディネーター | 指摘を実コードと仕様で裏付け、重複・誤検出を整理する。今回直すものと別 Issue の候補を分け、採用判断を人間に示す |
| 人間 | 実機の使いやすさと仕様上の判断を確認し、採用する PR を決める |

品質レビューは、まず `dual-implement` の **#8・#9 で試行**する。それ以外は明示的に指定された場合に追加する。PR ごとに実装・相互レビューとは別のセッションを使い、他者のレビュー結論を読む前に自分の確認結果をまとめる。相互レビューとの同時実行は可能だが、別の worktree を使い、同じファイルやコンテナを操作しない。役割名だけで品質が上がったとは判断しない。

### 対象コミットと確認結果

- レビュー開始前に PR の `headRefOid` を記録し、作業場所の `HEAD` と一致することを確かめる。相互レビューと品質レビューは同じコミットを対象にする。未コミットの変更があれば、そのままレビューしない。
- 相互レビュー担当は4つの必須チェックと、導入済みで対象となる E2E を実行する。品質担当は重複実行を必須にせず、構造とテスト内容を重点的に読む。実行が必要なら自身の隔離された作業場所で行う。
- 実行できないチェックは、理由と未確認の範囲を記す。CI・実装者の報告・自分で再確認した結果を区別し、未確認を「合格」にしない。
- 修正で head が変わったら、古いレビューはそのまま採用判断に使わない。更新差分と影響範囲を再確認し、新しい SHA と確認結果を残す。修正が不要だった場合も、報告時とマージ前に head が同じか確かめる。

### 指摘の書き方と扱い

1件ごとに、対象 SHA、ファイルと行、発生条件または具体的な影響、根拠（仕様・コード・再現結果）、修正案を付ける。確認できない懸念は、事実と分けて「未確認」と書く。

- **必須**：受け入れ条件を満たさない、仕様に反する、再現できるバグ・回帰など、今回の完了を妨げるもの。採用前に解消し、再確認する。
- **推奨**：具体的な保守・変更上の負担やテストの弱点があり、改善する価値があるもの。今回のスコープに必要なら修正し、独立した改善なら後続 Issue の候補にする。
- **好み**：振る舞いや具体的な保守上の影響がない表現上の違い。原則として採用を止める理由にしない。

推測上の将来要件に備えるだけの抽象化や、好みだけの全面改修を求めない。コーディネーターは各指摘を「確認できた／誤り／判断できない」に分け、確認できたものの対応先と、除外した理由を残す。

## 6. 証拠を残す

- **計画**：受け入れ条件と検証方法、仕様から決めた代表例・期待結果、モックを使う場合の理由、E2E の対象または対象外の理由。
- **PR**：対象コミット、実行コマンド・環境・結果、画面の幅・操作・結果、未確認の条件。期待値を変更した場合は根拠も残す。
- **ミューテーションテスト**：導入済みで対象となる場合は、7章の実行範囲・結果・生き残った変異の判断と対応先をPRに残し、レビューとIssueレポートへ引き継ぐ。
- **レビュー**：担当と役割、対象 SHA、読んだ周辺コードの範囲、自分で実行した確認と他者の証拠、指摘と残る不確実性。
- **[Issue レポート](issue-reports/README.md)**：両レビューの結果とリンク、コーディネーターの確認、修正後の再確認、採用理由。#8・#9 の品質レビューの試行では、相互レビューと重複しなかった有効な指摘、誤検出と除外理由、追加の所要時間も残し、継続するかの判断材料にする。時間を測れなければ推定値で埋めず「記録なし」とする。

試行の所要時間は担当ごとの開始・終了時刻で記録する。「追加待ち時間」は相互レビューがそろってから品質レビューがそろうまでの時間とし、品質レビューが先に終わっていれば0とする。品質レビューが無かった場合の全体時間を推測した値とは区別する。

## 7. ミューテーションテスト

2026-10-17に採用方針を整理した。**実行基盤は未導入**。[#19](https://github.com/dyamada-jaki/overstrata-board/issues/19)でStrykerJSのVitest連携を導入し、mainへ取り込んでから以下の実行・レビューを運用する。導入前のIssueに存在しないコマンドを要求せず、未実施と導入Issueへの参照を残す。

### 目的と対象

実装の比較演算子や条件式などを一時的に変え、既存テストがその誤りを検出できるかを確かめる。仕様から期待を決めるテスト先行を補完し、実装とテストが同じ仕様の誤解を持つ可能性は引き続きレビューで確認する。

- 初期対象は、距離・移動力・移動範囲の境界と占有判定、座標変換・盤面座標、マス選択の状態変化。それらを決める定数も対象とし、具体的な対象ファイルは導入計画と設定に明記する。
- 実行するテストは既存のVitest・React Testing Libraryを使う。2章の粒度を維持し、画面操作の結合テストから実物の処理を通して検出してよい。ミューテーションのためだけに内部関数を公開したり、関数ごとのテストやモックを増やしたりしない。
- テスト自身、型だけの宣言、CSS、生成物、雛形のサンプル、開発基盤のスクリプトは初期の変異対象に含めない。Playwrightを変異ごとに実行する構成は初期導入に含めず、実ブラウザの表示・操作と人間の実機確認は従来どおり続ける。

### 開発サイクルへの組み込み

1. **計画**：基盤の導入状況と対象範囲を確認し、今回の振る舞いで見つけたい誤りを具体例で挙げる。対象コード・関連テスト・実行結果に影響する設定や依存を変える場合は、ミューテーションテストも計画する。
2. **実装・検証**：通常テストが成功してからミューテーションテストを実行する。初期は設定した対象全体を確認する。生き残った変異に仕様上意味のあるテスト不足があれば、仕様から期待を決めてテストを補強し、通常テストとミューテーションテストを再実行する。正しい既存コードのテスト補強では、形式的なRedのために本体を壊さない。
3. **レビュー**：対象SHA・対象範囲・設定・レポートを照合し、以下の分類と除外理由を確認する。今回追加・変更した振る舞いについて、意味のある未検出を理由なく残さない。仕様違反・回帰は通常の必須指摘として扱い、独立した既存テストの改善は対応するIssueへ引き継ぐ。
4. **ふりかえり**：今回見つかったテスト不足、補強後の検出、残件、実行時間を同じIssueレポートに残す。前回の改善を確かめられたか、対象外で確かめられなかったかも区別する。

### 結果の判断

| 結果 | 扱い |
|---|---|
| Killed（テストが失敗した） | 検出の証拠。重要な例では、対象の振る舞いによる失敗であることを確かめる |
| Survived / NoCoverage | テスト不足、仕様上同じ結果になる等価な変異、対象外の入力・振る舞い、判断待ちに分け、根拠と対応を残す。「おそらく等価」だけでは解決済みにしない |
| Timeout | Strykerでは検出に算入されるが、assertionによる検出と分けて報告する。環境の遅さや実行障害と疑われる場合は原因を確認する |
| CompileError / RuntimeError / Ignored / Pending等 | テストが誤りを検出した件数に混ぜない。無効な変異、設定・実行障害、除外・未完了を区別し、未実施の結果を合格としない |

- **導入時は一律のスコア閾値や100%を必須にしない。** 生き残った変異の内容を確認することを必須にし、導入時の基準値と実例から数値による合否判定の必要性を評価する。通常テスト・変異前の初期実行・ツールの実行失敗は、スコア閾値とは別に失敗として扱う。
- 等価・対象外と判断した変異は、仕様の範囲と理由を記録する。スコアを上げるために仕様を追加したり、検出しにくいファイルや演算子を一括除外したりしない。必要な除外は狭く指定してレビューする。
- PRには、対象SHA、ツールの版、コマンド・環境・実行時間、変異対象、状態別件数・スコア、HTML/JSONレポートの場所、Survived/NoCoverageと除外の判断・対応先を残す。対象や設定が違うスコアをそのまま比較しない。
