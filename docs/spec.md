## 1. このアプリは何か

TRPG「Overstrata」の**プレイ中に使う戦闘ボード**。戦場のマス目・キャラの位置・移動できる範囲を画面に出す。

- **使う場面**: 音声でプレイしている卓で、戦闘中の位置関係をみんなで確認する
- **目標**: GM とプレイヤーが、それぞれの端末で同じ盤面を見て操作できること
- **最初の形**: 1台の端末で、誰か1人が操作して画面を見せる。複数端末での共有は後のスプリントで入れる（→ 4章）
- **入力**: キャラや位置はアプリ上で手入力する（AI-GM の出力を読み込むのは将来）

### 原則: ルールは補助のみ（自由優先）

アプリはルールを**強制しない**。移動範囲などを「見せる」だけで、最終判断は GM とプレイヤーがする。
例: 移動範囲の外にもキャラを動かせる。

### 実行環境: 開発も本番もコンテナで動かす

- Docker で動く前提にする（OrbStack など Docker 互換のランタイムでもよい）。ホストに Node を入れなくても開発できるようにする
- **開発**: `docker compose up` で開発サーバーが起動し、ホストのブラウザで開ける。テスト・型チェック・Lint・ビルドもコンテナの中で実行できる
- **本番**: ビルドしたファイルを Web サーバーで配信するイメージを作る。アプリ自体はサーバー処理を持たない（ブラウザだけで完結する）
- どこにデプロイするかは決めていない（→ 4章「次のスプリントの候補」）

## 2. 画面と操作

### 2.1 盤面

- 正方形のマス目
- **大きさは戦場ごとに変わる前提**。初期値は **10×10**（画面から大きさを変える機能は将来）
- 座標ラベル: 列は A, B, C…（左から）、行は 1, 2, 3…（上から）。左上のマスが **A1**
- 座標は「**C4**」のように列→行の順で、ハイフンなしで書く（音声で「C4へ移動」と言えるように）
- マスをタップすると、そのマスを選べる

### 2.2 キャラ

- 盤面にはキャラがコマ（トークン）として置かれる。1マスに1体まで
- キャラが持つ情報（最初の段階）
  - 名前
  - 味方か敵か（色で見分けられるようにする）
  - 装備の重さ: 軽装 / 中装 / 重装（移動力が決まる → 3.2）
- 最初はサンプルのキャラ4体（味方2・敵2）が置かれた状態で始まる。画面からの追加・削除は将来

### 2.3 移動

1. キャラをタップすると選択され、**移動できる範囲**が色つきで表示される
2. 空いているマスをタップすると、キャラがそこへ移動する
   - 範囲の外の空きマスにも移動できる（1章の原則）
   - 他のキャラがいるマスには移動できない
3. 移動すると選択が解除され、範囲の表示が消える。選択中のキャラをもう一度タップしても解除される

移動できる範囲 = 移動力（3.2）以内の距離（3.1）にあり、盤面の中で、他のキャラがいないマス。
他のキャラを「通り抜けられるか」はまだ考えない（→ 5章の未決事項）。

### 2.4 画面の前提

- スマホの縦画面（幅 375px）を基準に作る。PC でも崩れなければよい
- 10×10 の盤面は、幅 375px で横スクロールなしに全体が見え、マスを指でタップできる
- 画面の文言は日本語

## 3. ルールの扱い

ゲームのルール本体はこのリポジトリの外にある。ここにはアプリに関係する部分だけを書く。

### 3.0 ルールの正本はどこにあるか

- ゲーム設計の正本は別リポジトリの Obsidian vault（`dyamada-jaki/overstrata`）。このリポジトリには含まれない
- アプリに関係するのは `00_meta/コア設計.md` の **§6.6 行動経済（位置・移動・1手番・足止め）** と **§6.8 射程・範囲・盤面の数え方**。決定の経緯は `00_meta/決定事項ログ.md`、数値検証は `60_playtest/`
- `30_rules/` は目次だけの空の器で、ルール本文はまだ入っていない（2026-09 時点）
- vault の `20_gm_secret/` と `layer: GM` のファイルは GM 専用。**このリポジトリ（コード・Issue・PR・ドキュメント）に内容を書かない**
- vault は**読むだけ**。アプリ側の都合で vault を書き換えない（ルールを直す判断は設計の席で人間がする）

### 3.1 距離の数え方（移動）

**縦・横は1マス=1。斜めは1マス目=1、2マス目=2、3マス目=1…と交互に数える。**

横の差を dx、縦の差を dy とすると: 距離 = `max(dx, dy) + floor(min(dx, dy) / 2)`

| 動き | 距離 |
|---|---|
| 右へ3 | 3 |
| 斜めに1 | 1 |
| 斜めに2 | 3 |
| 斜めに3 | 4 |
| 斜めに4 | 6 |
| 右へ4・下へ2 | 5 |

向きが逆でも距離は同じ。

### 3.2 移動力

- 基本 **5マス**
- 装備の重さで補正: 軽装 ±0 / 中装 −1 / 重装 −2（つまり 5 / 4 / 3）
- この数値はゲーム側で仮の値。後で変わる前提で扱う

### 3.3 将来の機能で使うルール（まだ作らない）

- 1手番の行動は次の5つのどれか1つ（移動を攻撃の前後に分けない）: ただ近づく / 近づいて攻撃 / その場で攻撃 / 攻撃して離れる / ただ離れる
- すれ違いざまの攻撃（機会攻撃）という概念はない
- 手番の順は敏捷の高い順で固定。自分の手番に「そのラウンドの最後まで遅らせる」を選べる。遅らせた者同士は元の敏捷順に並ぶ

## 4. 作る順番と、今はやらないこと

### Sprint 1（Walking Skeleton）

画面で「戦闘が見える」最小の形を、端から端まで一通り作る。

1. 雛形と CI
2. 盤面の表示（2.1） ─┐ 並行できる
3. 距離と移動範囲の計算（3.1・3.2） ─┘
4. サンプルキャラ4体の表示と移動（2.2・2.3）

### 次のスプリントの候補

- キャラの追加・削除
- 手番の管理（敏捷順・遅らせる）
- 行動5パターンの記録
- HP の増減
- 状態の保存（今はリロードで初期配置に戻ってよい）
- デプロイ
- 複数端末での共有（方式は着手前に議論する）

### 今はやらないこと

- 画面から盤面の大きさを変える
- 地形・障害物
- 射程・範囲の表示
- AI-GM の出力の読み込み

## 5. 未決事項

| 論点 | 当面の扱い |
|---|---|
| 他のキャラのマスを通り抜けられるか。ゲームには「前衛のマスとその隣は敵が素通りできない（前衛＝動く壁）」という考え方がある | 移動範囲は「他のキャラがいるマスを除くだけ」。通り道は考えない |
| 斜めに並んだ2体の間を、斜め移動で抜けられるか | 同上 |
| 射程・範囲の数え方。ゲーム側は「縦横どちらの差も N 以内なら射程 N」（斜めも1と数える）。移動の数え方（3.1）と揃えるか | 射程表示を作るときに決める |
| 複数端末で共有するとき、誰が何を動かせるか。同期の方式 | 共有に着手する前に決める |
| 大きな盤面（20×20 など）をスマホでどう見せるか | 盤面サイズの変更を作るときに決める |
| 地形・障害物をどう扱うか | 今はやらない |

## 6. 決定の記録

- 2026-09-25: 構想（用途・手入力・補助のみ・距離の数え方・技術・10×10）

### ゲーム設計（vault）との関係

このアプリの仕様を決める過程で、vault の記述と食い違った点と、その決着。

| 論点 | 決着 |
|---|---|
| 移動の数え方 | vault の `コア設計.md` §6.8 は当初「移動＝縦横のみ（斜め移動なし）」だった。**斜め交互 1→2 を採用**し、vault 側にも記録済み（2026-09-28） |
| 端末の数 | vault の §6.6 は「1台を全員で囲む」。このアプリは**複数端末での共有を目標にする**（相棒の決定）。vault 側をどう直すかは設計の席の判断に委ねる |
| 盤面サイズ | vault の §6.8 は通常戦闘 20×20 前後が目安。このアプリは**可変が前提で初期値 10×10**（スマホで 20×20 をどう見せるかは 5章の未決事項） |
| 座標の表記 | vault は「B4」「C7」。これに揃えて**ハイフンなし**にした |
