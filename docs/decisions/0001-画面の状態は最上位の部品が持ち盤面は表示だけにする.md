# 0001. 画面の状態は最上位の部品が持ち、盤面は表示と操作の通知だけにする

- 状態: 採用
- 日時: 2026-10-23 17:00 JST（人間が採用した日時）
- 関連: Issue #32 / 採用 PR #38 / [Issue レポート](../issue-reports/issue-32.md)

## 背景
#9（PR #35）では、`Board` が `characters` prop を初期値として写し、自分で駒と選択の状態を持っていた。#32 で、駒の用意・配置・確定・準備のやり直し・新しい戦闘への切り替えが加わり、未配置一覧と盤面が同じ駒と選択を扱う必要が出た（[spec.md 2.2](../spec.md#22-キャラ)）。

## 決定
- 駒・選択・段階（数の指定／配置中／確定後）の状態は、画面の最上位の部品（#32 時点では `App`）が `useState` で1か所に持つ
- `Board` は状態を持たない。受け取った状態を表示し、マスのタップを通知するだけにする
- 状態の変化（選択・配置・移動・確定）は `src/domain/` の純粋関数で計算し、画面はその結果を入れ替える

## 理由
- 準備のやり直しや新しい戦闘で、全駒・選択・段階・入力をまとめて初期状態へ戻せる。prop を初期値として写す作りでは、外から入れ替えられない
- 一覧と盤面が同じ選択を共有でき、「未配置の駒を選んで空きマスに置く」「別の駒で選択だけ切り替える」を1つの状態で扱える
- 二重実装の両 PR（#38・#39）が、状態を上の部品へ移し `Board` を表示だけにする点で一致した

## 選ばなかった案
- `Board` が prop を初期値として状態を持つ（#9 の作り）：全体のクリアや一覧との共有ができない
- 画面専用の部品（`BattleScreen`）を新しく作り、段階の進め方まで domain の状態関数にまとめる（PR #39）：方向は同じだが、#32 の範囲では `App` に置けば足りた。画面が増えたら、その部品へ移すことは本 ADR の範囲内

## 影響
- #37（駒ごとの移動力）・#33（途中の増減）・#34（倒れた表示）は、同じ状態に項目や操作を足す形で作る。`Board` に状態を戻さない
- 盤面のテストは、状態を渡して表示と通知を確かめられる。画面の流れは最上位の部品を描画した結合テストで確かめる
- 複数端末の共有を入れるときは、この状態の持ち主をどこに置くか（サーバーとの同期）を見直すきっかけになる
