# 技術判断の記録（ADR）

Issue を越えて効く技術・設計の選び方を、1件1ファイルで残す（ADR: Architecture Decision Record）。
次の Issue の計画で「前にどう決めたか、なぜか」を読めるようにし、同じ議論を繰り返さないためのもの。

## 何を書くか

| 書く | 書かない（戻す先） |
|---|---|
| 状態を持つ場所と部品の責務の分け方、データの形、ライブラリやツールの採用、テストの基盤の選び方など、**次の Issue の計画を変える技術の判断** | ゲームのルール・画面の振る舞い・プロダクトの決定（spec.md）。進め方・スキル・席の決まり（workflow.md・スキル）。1つの Issue の中だけで済む実装の選択（PR 本文・Issue レポート） |

迷ったら「この判断を知らずに次の Issue を計画すると、作り直しや食い違いが起きるか」で決める。起きないなら書かない。件数を増やすことは目的にしない。

## いつ・誰が書くか

1. **気づく**（④計画承認）: 開発チームが、計画に Issue を越えて効く選び方が含まれていれば「ADR の候補」として控え、人間に見せる。二重実装では2つの計画で選び方が違うことがあるので、ここでは書かない
2. **書く**（⑧ふりかえり）: 開発チームが finish-issue で、採用した PR の選び方をもとに ADR の案を示し、人間が採用したものだけをこのフォルダに保存する
3. **読む**（次の計画）: 実装者と開発チームは、計画の前に下の一覧と関係する ADR を読む。ADR と違う選び方をするなら、計画でそう書いて理由を示す（勝手に外れない）

PO はプロダクトの判断を spec.md に書き、ADR は書かない。ADR の候補に気づいたら開発チームへの申し送りか、人間との相談で出す。

## 書き方

- ファイル名は `番号-題名.md`（例: `0001-盤面の状態を持つ場所.md`）。番号は4桁の通し番号で、使い回さない
- 雛形は [0000-template.md](0000-template.md)。1件は短く、1画面に収まる程度にする
- 日時は、保存した日時（人間が採用した日時）を `YYYY-MM-DD HH:MM JST` で書く。同じ日に Issue レポートやコミットと並べて追えるようにするため
- 決めたことは書き換えない。誤字や、リンクの追加・状態の更新だけは直してよい
- 判断を変えるときは、新しい ADR を書いて前の ADR を置き換える。前の ADR は状態を「置き換え済み（→ 番号）」にし、一覧も直す
- GM 向けの秘匿情報、認証情報、環境変数の秘密の値は記載しない

状態は次の2つ。

| 状態 | 意味 |
|---|---|
| 採用 | 今の作りはこれに従う |
| 置き換え済み（→ 番号） | 後の ADR で判断を変えた。経緯として残す |
