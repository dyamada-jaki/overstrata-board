# 0006. CI のミューテーションの省略は、実際に検証したツリー（記録したマージ SHA）との差分で決める

- 状態: 採用
- 日時: 2026-10-26 12:11 JST（人間が採用した日時）
- 関連: Issue #47 / 採用 PR #52 / [Issue レポート](../issue-reports/issue-47.md)

## 背景
#47 で、Markdown だけの変更では CI のミューテーションテスト（約23〜36分）を省略することにした。省略してよいと言うには、「どこかで全対象のミューテーションが成功している」ことと「そこからの差分が Markdown だけ」であることを示す必要があり、その比較元を何にするかを決める必要があった。

## 決定
- 比較元は、全対象のミューテーションが成功した run が**実際に検証したツリー**とする。PR の run では GitHub が作るマージ SHA（`GITHUB_SHA`）を検証しているので、成功時にその SHA を artifact の名前（`mutation-verified-<sha>-<attempt>`）に記録し、次の run はそこから今の対象までのツリー差分を見る（`scripts/mutation-ci.mjs`）
- 差分のすべてのパスが `.md` で終わるときだけ省略する。API・履歴・差分の取得に失敗したとき、再実行（attempt > 1）、比較元と対象が同じ SHA のときは全対象を実行する
- 今後、CI の省略・キャッシュ・前の結果の再利用を足すときも、「実際に検証した内容」を記録してそれと比べる。API が返す別の SHA（PR の head など）で代用しない

## 理由
- GitHub API の workflow run が返す `head_sha` は PR の head で、実際に検証したマージ SHA ではない。head 同士を比べると、main 側でコードを取り消した（revert した）場合に、検証していない組み合わせを Markdown だけの差分と誤って省略しうる（PR #51 への相互レビューの必須指摘）
- 検証したツリーそのものと比べれば、比較元をどう選んでも、検証していない内容は省略されない
- 二重実装で比べ、PR #52 の作りを人間が採用した

## 選ばなかった案
- 前回成功した PR の head SHA を比較元にする（PR #51）：上の取り消しの場合に安全でない。fixture も「main ではコードが足されるだけ」という同じ前提で作られていて、試験で検出できなかった
- 並列数を上げて全体を速くする：CI（4 CPU）で並列数4にすると Timeout が4件から52〜66件に増え、時間も短くならなかった。並列数は2を維持する

## 影響
- 省略やキャッシュの判定を試験するときは、代表ケースに取り消し・巻き戻しを含める
- 全対象を実行した run だけが証拠を残すので、artifact の保存期間が切れると次は全対象を実行する（安全側）
- 判定の結果（比較元・範囲・理由）は CI の Summary と `ci-decision.json` に残る。比較元の表示を分かりやすくする改善は、PO への申し送りに後続の案として残した
