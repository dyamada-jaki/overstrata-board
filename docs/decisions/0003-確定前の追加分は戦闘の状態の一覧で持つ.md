# 0003. 戦闘途中に追加して確定前の駒は、戦闘の状態の一覧（`pendingIds`）で持つ

- 状態: 採用
- 日時: 2026-10-25 JST（人間が採用した日時）
- 関連: Issue #33 / 採用 PR #43 / [Issue レポート](../issue-reports/issue-33.md)

## 背景
#33 で、戦闘の確定後にも駒を追加できるようになった。追加した駒は「追加分を確定」を押すまで、移動力の変更や削除ができ、確定すると既存の駒と同じ扱いになる（[spec.md 2.2](../spec.md#22-キャラ)）。どの駒がまだ確定前かを、どこに持つかを決める必要があった。

## 決定
確定前の追加分は、`BattleState.pendingIds`（駒の `id` の一覧）で持つ。
- `addPieces` が戦闘の確定後に追加した駒の `id` を足し、`confirmAdditions` が空にする。`removePiece` は削除した駒の `id` を一覧からも外す
- 一覧を変えるのは `src/domain/preparation.ts` の純粋関数だけにする。画面（`App`）は一覧を直接書き換えない
- `Character` には確定前かどうかの項目を足さない

## 理由
- 確定前かどうかは、駒そのものの性質ではなく、戦闘の進み具合（準備・確定後・追加の確定前）に属する。戦闘の状態として持つと、`Character` と #9 のサンプルデータを変えずに済む
- 一覧の同期は domain の関数に閉じており、削除したときに一覧からも外れることを domain のテスト（`src/domain/piece-management.test.ts`）で確かめている
- 二重実装の比較で、人間は両方の作りを計画として承認し、受け入れ条件・テスト先行・ルール計算の置き場所を見て PR #43 を採用した

## 選ばなかった案
- 駒に `confirmed` を持たせる（不採用 PR #44 の作り）：表示と押せるかを毎回の計算で決めるので、同期が要らない利点があった。[ADR 0002](0002-駒は番号と移動力と未配置を自分で持つ.md) の「別の一覧で持つと同期が要る」という考え方にはこちらが近い。採らなかったのは、PR #44 が他の点（判定の画面側への重複など）で採用されなかったためで、この作り自体の欠点が見つかったからではない

## 影響
- ADR 0002 とは向きが違う。0002 は「駒の配置の有無」を駒自身の `position` で持つ。この ADR は「戦闘の中での段階」を戦闘の状態で持つ。駒を消す・増やす関数を足すときは、`pendingIds` の同期を同じ関数の中で行い、domain のテストで確かめる
- #34 の倒れた状態など、駒の状態を増やすときは、駒の性質か戦闘の段階かを計画で書き、この ADR と 0002 のどちらに沿うかを示す
- 同期の漏れによる不具合が出たら、駒に持たせる案（`confirmed`）への置き換えを検討する
